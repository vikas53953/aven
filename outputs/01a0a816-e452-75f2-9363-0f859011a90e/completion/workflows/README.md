# Clarification and approval workflow candidate

This candidate slice contains a backend lifecycle module, a structured chat/runtime bridge, a mountable HTTP adapter, and a browser card renderer. They keep clarification and approval state separate from provider selection and never perform a live provider, browser, desktop, or network-device operation.

The public lifecycle is:

1. A normal model response calls the typed local `ask_clarification` tool or returns the validated JSON content envelope `{ type: 'pending_question', prompt, choices, allow_free_text, context }`; compatibility extraction also accepts equivalent tool-result shapes. `ClarificationRunManager.start()` returns a visible waiting card with a one-time token plus only whitelisted provider metadata; an absent response provenance is reported as unavailable rather than invented. Creating a newer question marks an older pending card stale. The normal `/api/chat` fixture proves the same run/chat and provider selection resume through `/api/chat/workflow/answer`.
2. `answerQuestion()` or `cancelQuestion()` consumes the question token. The answer is exactly one offered choice or permitted free-text value. After a browser refresh, the tokenless restored card offers an explicit run/chat-scoped `abandon` action that cancels only the server-side wait and permits a fresh request; it never resumes silently.
3. `createProposal()` records an exact target, operation, scope, diff, impact, rollback description, mode, and stable `scopeDigest`/`actionDigest`.
4. `reviewProposal()` persists an immutable change-review receipt. `renderQuestionCard()`, `renderProposal()`, and `renderApprovalCard()` are pure projections and never call an executor.
5. `requestApproval()` binds a pending approval to the proposal revision and both digests. `approveApproval()`, `denyApproval()`, and `cancelApproval()` consume the decision token; approval returns a separate one-time execution token.
6. `execute()` verifies the current proposal, exact scope/digest, expiry, and execution token before consuming it. Only `{ kind: 'mock', execute() }` executors are accepted in this candidate. A thrown mock execution is recorded as `unknown`, and the consumed token cannot be replayed.

`ClarificationRunManager` reports `running`, `waiting-question` (`terminal: false`), and the eventual `completed`, `failed`, or `canceled` terminal status through `onStatus`, including bounded sanitized run events. The host reliability ledger can therefore settle the same run as waiting and later terminal without treating a non-null pending reply as success. Every answer, stop, proposal, approval, and execution operation carries the originating `runId` and `chatId`; resumed segments keep the original run and selection while receiving a fresh cancellation segment. The browser shows a running resumed card with an explicit Stop action, and a tokenless refresh card exposes explicit abandon before a fresh request.

`candidate/clarification-server-adapter.cjs` exposes POST start/answer/cancel/abandon/stop, run review, proposal, approval, and mock execution endpoints for the host server to mount after its existing origin policy. Proposal and approval operations require the persisted run/chat ownership binding. `candidate/polished-approval-workflow.js` renders pending-question, exact-scope review, approval, and explicitly labeled approved/mock receipt cards. Rendering and proposal review do not invoke callbacks.

Pass a `storagePath` to persist hashes, state, ownership bindings, events, and review receipts. Raw decision or execution tokens are never written to that file. The SQLite state store uses an atomic `BEGIN IMMEDIATE` transaction and revision CAS; stale owners must reload. Commit failures restore the last durable state. Reload validates proposal, question, approval, receipt, and ownership relationships and digests, records an explicit reload result, and invalidates pending clarification interaction tokens plus pending/approved execution capabilities so a fresh question and approval are required; answered clarification history remains available for digest binding and review receipts. The browser keeps current one-time auth tokens only in an in-memory map; its persisted conversation state is tokenless, and reload renders retained history as non-interactive. Resumed model segments receive fresh cancellation signals and preserve the original run identity. `ClarificationRunManager.close()` aborts active segments, clears its volatile run map, and closes the workflow only when it owns the workflow instance; a host server can therefore dispose its default durable manager without closing an injected shared workflow. `replacements.json` contains exact, minimal server/runtime/UI integration hunks for the root agent to review and apply; no live product file was edited here. See `sourcehashes.json`, `row-results.json`, and `evidence.json` for the handoff record.
